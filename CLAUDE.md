# Micro E-Racer

A Micro Machines–style 3D racing game in the browser, online first. You enter a name, press Play, and take over a Bot's E-Car in a Race that is already running, against up to 7 others (Players or Bots). The E-Cars are electric: Energy drains as you drive and when you are hit, Batteries on the Track charge it, and an empty E-Car is Stranded and then Recharged by a drone where it stands. There are Shots, Item Boxes (Missile, Mine, Shield), Rams, Drifts, Puddles and Fall-offs on 50 small Tracks round 22 places, from a kitchen table to London, Las Vegas and Heidelberg; you pick one on the start screen or take any Race. It runs on desktop and mobile.

It is TypeScript throughout: Three.js in the browser (built with Vite), Colyseus on a Node server, and our own small physics in both ([ADR 0002](docs/adr/0002-own-physics-instead-of-rapier.md)). It is also a native app for iPhone and iPad in `ios/`: a Swift port (SwiftUI, SceneKit, the Colyseus Swift SDK) that races in the same Races as the browsers, with an Apple Watch app beside it that races the Bots offline. Every model, texture, sound and song is generated in code, and so is the picture a shared link shows. The only asset files are the Bangers font (`@fontsource/bangers`; the app bundles a copy of the same WOFF), the Racers' voices (short CC0 recordings in `client/public/voices`, credited in its `CREDITS.md`) and the icon: one picture, `client/public/icon.png` (192 px) for the browsers and its 1024 px original in the apps' asset catalogs. The scenery of every theme beyond the first four reaches the apps as `ios/Shared/Resources/Themes.json`, written from the web's own data (`npx tsx ios/themes.ts`).

- **Terms:** [CONTEXT.md](CONTEXT.md) is the glossary (Race, Seat, Player, Bot, E-Car, Body, Energy, Stranded, Recharge, Ram, Hit, Item…). Use its capitalised terms in code, comments and UI text. A new or changed game concept gets its entry there. It is a glossary only, so no implementation details go in it.
- **Decisions:** [docs/adr/](docs/adr/). An ADR is only for a decision that is hard to reverse, surprising without context and the result of a real trade-off.

## Running and checking

- `npm run dev` starts Vite on `:5173` (with `--host`, so a phone on the LAN can join) and the game server on `:2567` (`tsx watch`). In development the browser connects to `<hostname>:2567`; in production, to its own origin.
- `TRACK=garden` picks the first Race's Track, and `DRAIN_SCALE=10` makes Energy run out ten times faster (for trying out Stranded and the Recharge). Both work with `npm run dev` and in `/etc/default/micro-eracer` on the server.
- The app's App Store page is `APP_STORE` (`shared/src/version.ts`, `ios/Core/Version.swift`): the browser offers it on an iPhone or iPad (a dialog over the start form, and Safari's Smart App Banner, `apple-itunes-app` in `index.html`, which carries its id), and `/version` hands it to the apps for their update dialog. `APP_STORE_URL` in `/etc/default/micro-eracer` puts another page there in its place.
- The user usually has `npm run dev` running. Start any server of your own on another port (`PORT=2600 npx tsx server/src/index.ts`) and never kill theirs.
- After every change, run these from the repo root:
  - `npm run typecheck` (`tsc --noEmit`; nothing is emitted, since Vite and tsx run the TypeScript as it is).
  - `npm test` (`shared/src/*.test.ts` and `client/src/*.test.ts`, node:test through tsx). `race.test.ts` checks that every Track closes and counts Laps only in order. It runs a headless Race on every Track in which 8 Bots must finish, and checks Stranded → Recharge and Shield. It logs balance stats per Track: Race time, Recharges, Leader Recharges, pickups, Rams, Hits. Extend it when you add a mechanic, and look at the stats after balance changes. Running dry should be common, most of all at the front (the Leader about once a Race in Bot-only Races). `themes.test.ts` checks that every data prop fits in its tile, that a theme's river runs under a walled bridge and its big landmarks find room on each of its Tracks, and that the apps' `Themes.json` is up to date: after changing `client/src/themes/`, run `npx tsx ios/themes.ts`. `physics.test.ts` replays `physics.fixture.json`: set-ups, and where each E-Car is after every 10 steps.   - `npm run build`, to confirm Vite bundles cleanly, with no chunk-size warning. The build (`client/vite.config.ts`) puts the libraries in a `vendor` chunk and writes a Brotli copy (`.br`) of each script and stylesheet, which the server sends instead (Caddy only compresses on the fly, about 20% bigger). It also draws the link preview card and warns if it grows past WhatsApp's 300 kB.
- After a change to `shared/`, to what the room sends (schema, messages, `RaceEvent`), to anything a player sees or hears, or to `ios/`, also check the iOS app, from `ios/`:

### Core model

- **Who owns what** ([ADR 0001](docs/adr/0001-browsers-drive-own-car-server-owns-the-rest.md)):
  - **The browser:** each browser simulates only its own E-Car, as a dynamic body in its own `World` of the Track. It sends a `pose` 30 times a second, and handles its own Fall-off (back to the last Checkpoint).
  - **The server owns everything else:** Bots (dynamic bodies driven by `botInput`), Laps and Positions, Energy, Batteries, Rams, Combat, phases and results. Players' E-Cars are kinematic bodies on the server, placed from their poses. `World.touching` still reports when two kinematic bodies touch, so the server can judge Rams between Players.
  - **What the server does to a Player's E-Car** reaches the browser in one of two ways, never by moving the server's body:
    - a Hit's shove and spin come as a `hit` event, and that browser applies them;
    - a jump (a new grid) bumps `Seat.spawn`. The browser teleports to the reported pose when it sees the new `spawn`, and the server ignores poses that carry an old `spawn`.
- **Track:** a turtle walk of pieces on a grid of `TILE` = 16 m tiles: `S`, `L`, `R`, the ramps `U`/`D` (`RISE` = 3.5 m, eased at both ends) and the jump `J` (a kicker that ends in a drop); a trailing `*` adds walls. It is sampled into `samples`, each with its road height `y`. Checkpoints, the Bot racing line, Puddles and Item Box spots all come from piece indexes. Progress (`Progress.u`) is a continuous sample count found by a windowed nearest-sample search. That stops shortcuts: a Lap only counts when the samples are passed in order. Every Track must close at the height it started, which `npm test` checks.
- **Heights:** a Track may cross itself only on different levels (a bridge); `buildTrack` throws on a crossing at one height. Anything that finds things by position must stay on its own level: `nearestSample` is 3D, and pickups, Hits, Puddles and Mines check `sameLevel`. A Fall-off is `FALL_Y` below the road under the E-Car's progress, which also catches a drop from a bridge onto the road beneath. The bodies never pitch: on a ramp one edge rides the road, so `driveCar`'s check for road under the middle (`World.onRoad`) reaches far, and the browser tilts the models along the road under them and sets them down without sinking in (`place` in `motion.ts`, checked by `motion.test.ts`). The others' eased height lags on a ramp, so while the server has one on the road, `place` draws it on the road where it is shown.
- **Physics** ([ADR 0002](docs/adr/0002-own-physics-instead-of-rapier.md)): `physics.ts` steps the E-Cars as boxes that only turn about the vertical axis, with gravity of 20 m/s². Each step finds the contacts first. A contact stops its two bodies where they would meet, or bounces them apart (0.3, above 1 m/s; never off the road). A contact off a body's middle turns it, and after the move any overlap left is pushed apart. The road is found from the samples near the body (`roadAt`, `roadUnder` in `collide.ts`: the highest road under 15 points of its underside). A wall only pushes straight out of its face, so an E-Car can't catch on the joins between its stretches. Anything new that bodies should collide with needs code in `collide.ts`.
- **Race flow:** `phase` goes grid → racing → finishing. Grid time is 3 s (`GRID_TIME`), counted down 3, 2, 1. The Race ends 5 s after the first finish (`FINISH_TIME`, counted down on the HUD) (meanwhile the HUD's standings fill up as Racers finish), then the next Race starts on another Track from the room's pool (`RaceSim.pool`): the Track its first Player picked again and again, any of the 50 at random where they picked Any Track, and only `CLASSIC_TRACKS` in the `race` room. There are 3 Laps and 8 Seats.
- **Offline Race:** when Play can't reach the server within 5 s, `main.ts` starts `offlineRace`: a `RaceSim` stepped in the browser behind `RaceLink`, the same interface as the room, so `game.ts` can't tell the two apart. Anything new the room does (a message, a state field) needs doing in `offline.ts` too.
- **Versions** (`shared/src/version.ts`, `ios/Core/Version.swift`): a client sends `protocol` (`PROTOCOL`) with its join, and asks `GET /version?protocol=` when it starts (the app also whenever it comes back to the front). Below `MIN_PROTOCOL` (no `protocol` counts as 1: the apps from before the check) `/version` says `compatible: false` and the room's static `onAuth` refuses the join with `OUTDATED` (426). The client then shows its update dialog (Reload in the browser; Update, to `APP_STORE`, in the app), and Play races offline. Bump `PROTOCOL` on both sides when an older client would race wrong against this server (the physics, `driveCar`, a rule a client applies to its own E-Car, a field renamed or removed), and raise `MIN_PROTOCOL` with it when the clients out there must stop racing online. That is a real trade-off: every app out is then offline only until the next one is through App Store review.
- **Tracks from the server:** online, the start screen offers the server's `GET /tracks` once it has answered, and the game builds each Race's Track from the room's `track` (`trackDefOf` in `state.ts`, `TrackSchema` in `OnlineRace.swift`), not from its own copy. So a Track the server adds or changes reaches the apps without an update, and caches of a built Track are keyed by its layout, not its id. What still needs the apps updated: a new theme (they leave its Tracks off the picker and draw them as the kitchen) and the staging of a changed Track on a data theme (the apps read it from `Themes.json`, and go without it for a layout they don't have). An Offline Race only races the Tracks the game came with.
- **Rams:** the victim is shoved along the contact as in a collision of the two weights (`ramResponse` in `contact.ts`: 65% of the closing speed between equal Bodies, with a bounce of 0.3), skids for a moment with little grip (`Car.slide`) and swings round if hit at the nose or tail. Between Bots the physics shares the momentum; a Bot rammed by a Player is shoved by the server, and a rammed Player's browser applies the shove from the `ram` event. The rammer's own browser can't push the others (they're kinematic there), so `ourRams` in `motion.ts` shoves the one it hits at once and keeps the rammer's way, and the server's event for that Ram is then skipped.
- **No stacking:** only the road counts as ground for `driveCar` (`World.onRoad`), so an E-Car on another's roof can't drive there, and after half a second the server puts it down beside the other at a free spot (`unstack` in `contact.ts`, `freeSpot` in `track.ts`, which the Fall-off reset uses too); for a Player through the `spawn` jump.
- **Joining and leaving:** only the first Player in a Race picks its Track: `race2` matches no option, so every join takes the fullest Race with a free Seat, and `track` only counts for a join that starts one. While a Race is running, the start screen shows its Track and how many Players are in it, and who (`GET /race`, from the room's metadata, asked every 5 s while the form is up) in place of the picker. A joining Player takes over the last-Position Bot's E-Car where it is, and everyone is told (`join`). Bot names start with 🤖 (`BOT_NAMES`) and Players' never do (`join` strips it); name tags are gold for Players and grey for Bots. A leaving Player's Seat goes back to a Bot (after a 5 s chance to reconnect).
- **Energy:** drains by distance driven: a full tank lasts `TANK_LAPS` = 1.6 Laps on any Track (times the Body's `tank`). Hits drain it. Below 25 the E-Car is in Limp Mode, down to half speed at empty. At 0 it is Stranded for `STRANDED_TIME` (it brakes to a halt, jerks and sputters while the drone flies in), then Recharged: the drone hovers over it and fills the battery where it stands, for `RECHARGE_TIME` at the back and, in the top three, until three, two or one Racers behind could get past (`rechargeLength` in `energy.ts`, at most 9 s). Meanwhile `HALT` holds it still, even on a ramp. The front three are held together (`leadPace` in `energy.ts`, sent to the browsers as `CarState.pace` in percent): the Leader is slowed from 2 m clear of second, down to 75% at 20 m; second the same against third, milder; and second and third get a tow of up to 6% when the E-Car ahead pulls away. In Bot-only Races second is within 20 m of the Leader about 90% of the time. Meanwhile the browser greys out its view (a CSS filter on the canvas, set in `hud.ts` only while needed).
- **Charging Station:** every Track has a bay `BAY_WIDTH` wide on the right of its last straights (`Sample.bay`, eased in and out; the road's collider is widened there, and `buildTrack` throws if there is no room). In it (`inStation`) an E-Car charges `STATION_RATE` a second under the `PIT_SPEED` limit, which the browser applies to its own E-Car. Bots low on Energy pull in and stay until nearly full.
- **Batteries:** each appears just ahead of one Racer picked by Position (`BATTERY_ODDS`: about 3% for the Leader up to 17–18% for each of the last four), and before the Racer in front of them, so nobody further ahead gets it first. That makes Energy plentiful at the back, fought over in the middle and scarce at the front, where the Charging Station is the way to keep going. Rams steal Energy.
- **Bots:** they hold off attacking for 4 s after GO (`botsAttack`). After that they hunt Batteries, Ram prey ahead (Players first), use Items when they make sense, and save their Shots mostly for Players. A Player in the lead is everyone's target: Bots behind them aim at them (leading the Shot) and together fire about once a second (`leaderShotAt` in `combat.ts`). `catchUp` keeps them near the Players.
- **Smooth over exact:** the room sends its state 30 times a second (`setPatchRate`). The browser draws its own E-Car between its last two physics steps, so it moves evenly at any frame rate, and moves the others every frame at their reported speed, only nudging them towards where the server says they are (`glide` in `motion.ts`). A late update shows as a little drift, never a jump; only an error over 6 m snaps.
- **Events:** `RaceEvent` (`ram`, `hit`, `boom`, `block`, `battery`, `shot`, `stranded`, `recharge`, `box`, `item`, `join`, `leave`) is what happened in one tick. It exists only to drive sounds and effects in the browsers; the state is the truth.
- **Look:** cel shading (`MeshToonMaterial` with a 3-tone gradient) with black outlines (`OutlineEffect`; `userData.outlineParameters = { visible: false }` turns one material's outline off), static scenery merged per material, canvas textures, a halftone overlay and comic HUD lettering.
- **Sound:** all WebAudio, started by the Play button (a user gesture, which mobile browsers need).
  - effects, and the airflow (filtered noise rising with speed; no motor hum) and skid of the Player's own E-Car
  - voices (`cry(mood, seat)`): CC0 recordings per mood (`CLIPS` in `audio.ts`, files `public/voices/<mood>-<name>.mp3`), played at a per-Seat rate so each Racer sounds different. Cries about other E-Cars are rationed, and ones about your own always play. A new clip must be CC0, trimmed, loudness-matched (about −18 dB mean, peaks under −1 dB) and listed in `CREDITS.md`
  - the chiptune songs of Electro Car Racer (github.com/cgrail/e-racer), taking turns across the Tracks in `TRACKS` order
  - one mute switch for everything

## Web and iOS stay in lockstep

The browsers and the apps are one product; the browsers and the iPhone app race in the same Races on the same server. A change to the rules (`shared/`), to what the room sends, or to what a player sees, hears or does in the browser is made in `ios/` in the same commit, or the two disagree mid-Race: an iPhone that drives differently puts its E-Car somewhere else than the server's Bots think, and Rams and Hits land wrong.

- **Where:** names of types, functions and constants are the same on both sides, so a grep finds the Swift; [ios/README.md](ios/README.md) maps each file. The game itself is in `ios/Core` and `ios/Shared`, which both apps compile, so a change there reaches the watch too; check that it still fits a watch (a small screen, the Crown and one tap, no network).
- **What catches drift:** `swift test` reads the web side's own files. After a deliberate physics change and `UPDATE_FIXTURE=1 npm test`, it fails until the Swift steps the same way again; a Track or song changed on one side fails it too.
- **The wire:** `OnlineRace.swift` reads the room's schema by field name and `RaceEvent(wire:)` decodes the events; a field renamed on the server reads as its default there. A phone may run an App Store build older than the deployed server for weeks, so the wire only grows: add fields, messages, event kinds and rooms, never rename or remove one (an old app drops events it doesn't know). Races are joined in the `race2` room; `race` stays for apps from before the Track picker and only races the four Tracks they know (`CLASSIC_TRACKS`), so a new Track never reaches an app that can't draw it. Apps that send `protocol` draw whatever Track the room sends, but the ones from before (which send none) only know these 50: with the next Track added, raise `MIN_PROTOCOL` to 2 (those apps then race offline), or give it a room (or a room option) they don't join. The Colyseus Swift SDK (0.18.x) must match the server's Colyseus (0.18): a new major needs a new app version out first.
- **Assets:** the apps bundle `client/public/voices` itself (a folder reference, not a copy), their own copy of `Bangers.woff`, and the icon (`AppIcon-1024.png` in each asset catalog, the same picture as the browsers' `client/public/icon.png`).
- **Saved data:** `UserDefaults` keys `name`, `body`, `muted`, `steer` and `side`, as in `localStorage`, with the same values (the watch also keeps its Track as `track`).

## Every change ends in the changelog

[CHANGELOG.md](CHANGELOG.md) is updated as part of the change, in the same commit, never afterwards and never in a batch.

- Write it under the top version section (`## <version> (current)`), in the group it belongs to, adding a group if none fits. The version is the app's `MARKETING_VERSION`; when that is bumped, the top section is closed and a new current one opens above it.
- One entry per change a player would notice: rules, controls, Tracks, the look and sound, what the start screen offers, what the wire carries. Refactors that change nothing observable stay out. Say what the game does now, not what the diff did.
- Both builds, one entry: there is no web and no iOS column, because a change that only reached one of them is a bug.
- [ios/WHATS-NEW.md](ios/WHATS-NEW.md) is the player-facing cut for the App Store, written when a version ships, not per commit. It is plain ASCII (App Store Connect rejects bullets, emoji and typographic dashes or quotes there).

## Rules for changes

- **Everything stays procedural:** no image, model, audio or font files beyond the bundled Bangers font, the CC0 voice clips and the icon. No requests to Google Fonts or other third parties (the audience is in Germany, so GDPR applies).
- **`shared/` runs in Node:** it must not touch the DOM or browser APIs, and it stays free of networking.
- **Server and browsers run the same `shared/` code:** a change to it, to the schema in `RaceRoom.ts`, to a message or to `RaceEvent` needs both sides deployed together. One process serves both, so a deploy does that, but tabs that are already open run the old client until they reload.
- **Never trust the browser:** every message is checked on the server (`isPose`: finite numbers, bounded; names cut to 16 characters; Body from `BODY_KINDS`), and Items (a Zap's Shots too) go through `canAct` and the server's own cooldowns.
- **Mobile is a first-class target:** touch steers anywhere on the screen but its buttons, one finger at a time (Buttons, the default: left or right of the steering pad's middle; Slider: drag; picked, like the pad's corner, `PadSide`, on the Practice Ground behind the start form's Controls button), has auto-throttle and one action button right above the pad (`#fire`: it shoots, or uses the Item when there is one, and `hud.ts` labels it), and no brake; a Back button (reverse) only shows while the E-Car is stuck (`showBack`, from `game.ts`), in the other bottom corner. Keep it to that, so a new action has to fit into the action button. On a phone the game must feel like an app, not a web page:
  - **Nothing zooms, pans or bounces.** The viewport meta has `minimum-scale=1, maximum-scale=1, user-scalable=no`, every element (`*`, since iOS doesn't reliably pass it down from `body`) has `touch-action: none`, and `html, body` have `overscroll-behavior: none`. iOS Safari ignores `user-scalable=no` and doesn't always honour `touch-action`, so `input.ts` also cancels its `gesturestart`, any touch move with two fingers down, `dblclick`, and any quick second tap wherever it lands (a button that was tapped still gets its `click`). On a desktop it cancels Ctrl + wheel (a trackpad pinch) and Ctrl or Cmd with + or −. Something that has to scroll (the start form) gets `touch-action: pan-y` on itself and everything in it, never `auto`, which would let it zoom again.
  - **Text fields are at least 16 px**, or iOS zooms in when one is focused.
  - **Holding a control only holds it:** every element has `-webkit-user-select: none` (Safari ignores the unprefixed `user-select`) and `-webkit-touch-callout: none`, and `input.ts` cancels `selectstart` and `contextmenu`, so a held thumb never selects text or opens the long-press menu. Only text fields get selection back (iOS can't type into them without it).
  - **Controls are for thumbs:** at least 44 px, in reach of the bottom corners, on pointer events (not `click` for anything held), and two at once must work (one thumb steering while the other fires).
  - **Layouts work at phone width in both orientations**, with anything at an edge inside the safe-area insets (`env(safe-area-inset-*)`; the viewport meta has `viewport-fit=cover`). Size with `100%`, `inset: 0` or `innerHeight`, never `100vh`, which is taller than the screen while the browser's bars show.
  - **Touch is `isTouch`** (`pointer: coarse`), never a user-agent check.
  - **Mind the GPU:** the pixel ratio is capped at 2, and `OutlineEffect` already renders everything twice, so mind the draw calls.
- **Per-Seat state lives on the `Seat`** (server) or in `views[seat]` (browser), never in globals.
- **Tracks are data:** a new Track is a file in `shared/src/tracks/` added to `TRACKS` (and to `TRACKS` in `ios/Core/Track.swift`), with a theme in `client/src/themes/` if it's new (its name in the `Theme` type on both sides; then `npx tsx ios/themes.ts`); `npm test` must pass on it, and every Body must get round it flat out (walls on the bends where it doesn't). On a theme with a river the bridge goes over the Track's highest, longest straight, which needs walls all along (its railings). A Track's id stays what it was when it is renamed: saved picks and the wire carry it.
- **Keep files under about 300 lines.** `game.ts`, `scene.ts`, `audio.ts` and `race.ts` are already past that. When a change makes one of them grow, split it along a real seam (effects out of `game.ts`, props per theme out of `scene.ts`, voices out of `audio.ts`, Bots out of `race.ts`) instead.
- **Saved data:** `localStorage` keys `name`, `body`, `muted`, `steer` and `side`, each read and written in `try/catch` (private mode), so the game works without storage. Old values must keep loading. The Track isn't saved: each visit starts on one at random.
- **Keep `README.md` in sync** when you add player-visible features, controls or settings.

## Workflow

- The backlog is `todo.md`, worked through with the `/todo` skill. Each item gets its own commit, and done items are ticked `[x]` and kept.
- Commit messages use an imperative subject of about 60 characters with no scope prefix ("Add soundtrack and systemd deployment"). Add a body only when the reason isn't obvious.
- Push every commit straight to `main`, without asking, once the checks above pass: no feature branches, no pull requests. A push to `main` deploys the server and the browser game, so never push red checks. The app ships separately, through the App Store, when the user releases a version. If the push is rejected because `main` moved, rebase onto `origin/main`, resolve any conflicts keeping both sides' intent, run the checks again and push. Never force-push `main`.
